# Architecture and validation boundaries

## Components

`manifest.json` installs two static `document_start` content-script groups on `https://m365.cloud.microsoft/*`, including `/chat`. Each group loads a single self-contained script. `page-hook.js` runs in MAIN so it can intercept the page's WebSockets; `content.js` runs in ISOLATED so it can use extension storage and retain tab metadata. The popup loads only `popup.js`. A classic background service worker, `background.js`, sets only the toolbar badge, title and icon from messages sent by Copilot tabs; it makes no network requests and needs no permissions beyond the `action` API every extension has. Each runtime script includes its helpers in a private lexical scope; there is no required `window.M365ExtenderCore` or separate shared script to load first. Popup page styles are embedded in `popup.html`.

Canonical editable files are in `src/`. `scripts/build.cjs` validates `src/models.json`, inlines it, and combines `src/core.js` with each entry point, adding `src/popup-ui.js` only to the popup bundle, to produce the four committed scripts in `extension/`. It also regenerates the model tables in the README and below from the same file. Run `npm run build` after source edits; `npm run check` and packaging reject stale bundles. Installation needs no build because the generated scripts are already included. This replaced the cross-file global dependency after a user reported an undefined `core.DEFAULT_TONE` startup error. The precise cause of the missing global in that installation was not established; this build removes that dependency altogether.

The hook proxies the WebSocket constructor to attach passive response listeners early. It also wraps the native prototype's `send`, checking only `wss://substrate.office.com/m365Copilot/Chathub/…` sockets. It preserves the native constructor's prototype, static constants, `instanceof`, and subclass behavior. Unrelated sockets pass through. JSON payloads are split/rejoined on `\x1e`; only type `1`/`4`, target `chat`, with an object at `arguments[0]` are modified. Every qualifying request uses the current preference, including follow-up turns.

## Startup and persistence

Two keys are saved: `selectedTone` (the default model) and `conversationTones`, a map from a hashed conversation ID to `{ tone, at }`. The popup keeps the 200 most recent entries; unknown tones in either key fall back to the default. The retired `inPageEnabled` setting is ignored. `chrome.storage.onChanged` updates the toolbar popup and hooks across tabs. Revision checks prevent a stale asynchronous initial read from overwriting a newer cross-tab update.

Because MAIN cannot read extension storage, the hook briefly holds the first chat request while the isolated script loads preferences. Later sends on the same socket retain their order behind it. If settings never arrive, the queue flushes after 1.5 seconds using Copilot's original tone and emits a visible warning; it never silently chooses a different forced model. Handshakes and pre-chat pings pass immediately. Socket close drops queued requests; native CONNECTING errors are preserved. No pending request is retried automatically.

## Conversation identity

Copilot's web client generates a `ConversationId` UUID per conversation and puts it in the Chathub socket URL's query string on every connection for that conversation, including the first message of a new chat; once a thread exists the page also navigates to `/chat/conversation/<id>`. Both sources are used by upstream browser automation (`aweussom/i-want-my-model-picker-back`, `driver.js`, which notes navigation can lag a turn), and the proxy (`cramt/m365-copilot-proxy`, API notes §8) reuses one ID across per-turn sockets. The hook extracts only this parameter (validated as 16–64 hex/dash characters, lowercased) and forwards it with each event. Other URL parts, including the access token, never leave MAIN.

The isolated script hashes each ID (SHA-256 of a fixed prefix plus the ID, first 128 bits) before using it as a storage key or sending anything to the popup; raw IDs exist only in tab memory. On each new connection it answers the hook with that conversation's tone or `null`. The hook holds a connection's first chat request until both the default and the conversation answer are known. If the conversation answer does not arrive within 1.5 seconds, it sends with the default, records `null` for that conversation so later turns are not held, and emits `conversation-unavailable`. A connection without a `ConversationId` uses the default with no wait.

The conversation the page is showing is the URL's ID when present. With no ID in the URL (a new chat), it is the conversation of the latest send, but only until the URL has shown that ID once; after that, a bare `/chat` page is treated as a new, unsent chat with no conversation readings and no per-conversation selector. Single-page navigation is observed through the Navigation API's `currententrychange` event.

## Quota metadata

The parser reads `frame.item` for type `2` final results and each `frame.arguments` value for type `1`, target `update`. It extracts only valid nonnegative integer `remainingAllowance` values, known result/origin enums, and numeric conversation counts. Both final and streaming responses update only valid fields they actually report. Metering merges valid per-budget readings; empty, absent or invalid fields retain the last reading. Omission does not mean zero or unlimited.

Only `GPT61SolQueryDaily` and `GPT61SolQueryWeekly` have direct evidence in the reviewed references for the six offered models. That model is marked as having a known paid-route cap. Other models with a prefix below recognize the exact `Daily`/`Weekly` suffixes **only if those keys are actually observed**. The evidence column is generated from `budgetEvidence` in `src/models.json`; the 25 October 2026 review behind it is in the [research notes](research.md#metering-keys-reviewed-25-october-2026).

The comparison ignores underscore differences and letter case. Unrecognized keys do not become model counters. No allowance is inferred from another model's map, no limits are hardcoded, and a missing value never becomes zero. New key formats require further research rather than guesswork. This limits automatic support to the budget shapes the extension can associate with a selected model; it cannot guarantee discovery of every future Microsoft usage cap.

Quotas are not persisted or shared between tabs, so accounts in different tabs are not mixed. Readings are split in two. Allowances (`metering`) are account-wide and follow the latest send in the tab, so a late reply on an older connection cannot overwrite them. Result, origin, applied tone, capacity and expiry belong to a per-conversation slot keyed by `ConversationId`, or by a sequential local socket ID when a connection has none; the tab keeps at most 50 slots. A slot accepts replies only after a chat was sent in it, so an idle pre-opened socket cannot inject readings, and a new socket in the same conversation keeps that conversation's readings. Every hook warning carries its socket and conversation; warnings about a just-sent chat (`settings-unavailable`, `conversation-unavailable`, `connection-closed`, `send-failed`) make that conversation current. Socket IDs are bookkeeping only, not account identity. The popup polls only the active tab's content script while it is open; this makes no Microsoft requests.

## Bridge and UI

The popup renderer also shows a compact conversation capacity meter and server expiry row. `conversationExpiryTime` is read from the same response containers as the other metadata, validated as a timezone-bearing ISO timestamp, normalized to UTC, and revalidated in ISOLATED before rendering a local date. There is no assumed expiry duration. The exact timestamp and a note distinguishing expiry from data deletion appear on hover or keyboard focus. Capacity uses reported message counts, clamps the visual fill to 100%, and highlights at 90%; zero/missing limits never create an invalid accessible meter. Final and streaming metadata without valid replacements retain prior capacity and expiry values. Result and origin also stay visible while the next reply is pending. These values remain tab-local and are not written to storage. Popup snapshot polling also refreshes the time-remaining text. No runtime files or permissions were added for these features.

Both worlds communicate via same-window, same-origin `postMessage` with an explicit channel and direction. The isolated script validates and filters incoming values. Page messages cannot directly write persistent preferences: only the popup control handler does so. MAIN uses a model allowlist for configuration. Host-page scripts can observe or spoof this bridge, as they can alter Copilot's own JavaScript, so it does not establish trusted model identity. Only sanitized metadata crosses it. Values rendered from settings or responses use `textContent`; the only HTML template is a static local UI string.

The content script sends the background worker `{ tone, remaining }` for the tab: the effective model (conversation choice or default) and its lowest reported daily/weekly allowance. The worker sets a per-tab badge from `badge` in `models.json` and colours the badge and icon at 20 or fewer (orange) and 10 or fewer (red) remaining. The coloured icons are drawn at runtime with `OffscreenCanvas` from the same shapes as `icons/source.svg`. When a tab starts loading, the worker resets it to the default badge; the content script re-sends its state after navigation settles.

No extension DOM or UI is injected into Copilot. The renderer is bundled only into the toolbar popup. The popup can change preferences even outside Copilot; tab metadata is available only when its content script is reachable. The UI does not claim that `DeepLeo` identifies a precise model version.

## Current limits and live acceptance checks

The MVP covers the top-level Copilot page's JSON Chathub WebSockets on the observed host. It does not intercept workers, cross-origin iframes, other Copilot domains, future transports, or MessagePack/binary chat frames. Reload the page after installation or extension updates. Site changes, tenant policies, agent routing, and Microsoft entitlement checks may affect behavior.

The Node suite exercises actual protocol and controller scripts in isolated VM contexts with mocked transport/storage. The browser fixture exercises the actual UI, popup controller, page hook, and isolated controller with simulated APIs in regular web frames. Neither test installs the MV3 extension into the user's real Chrome profile. A fresh VM with shared saved settings is used for restart-style tests; no physical browser restart is claimed.

Before declaring live support, load the unpacked extension on Windows Chrome, test all six selections in new and existing chats, and confirm that switching tabs and restarting Chrome preserves the selected model. Check that the observed applied tone matches outgoing DevTools frames and that usage values match sanitized type `2` final-item metering. Verify zero/absence handling and final-item refusal status. For per-conversation models, confirm in DevTools that the Chathub URL carries `ConversationId` for a new chat's first message and that it matches the later `/chat/conversation/<id>` URL; pin a model to one chat, then check that a second chat and a reopened first chat each send the expected tone. Check that the badge turns orange and red at the documented thresholds. Do not publish raw frames or account-bearing socket URLs. Live backend identity remains unresolved even when a request succeeds.
